# Assessments

The handbook has three kinds of learning artifact, and each does a different job:

| Artifact | Job |
| --- | --- |
| [Labs](../labs/README.md) | Teach one concept, in isolation, with runnable Java. |
| [Capstones](../capstones/README.md) | Compose concepts the labs already taught, around one realistic problem. |
| Assessments | Help decide which concepts a problem actually deserves — often fewer than you expect. |

A lab answers "how does this capability work?" A capstone answers "how do these capabilities fit together?" An assessment answers the question that should come first: "does this problem need them at all?"

**An assessment is not an automatic architecture generator.** It does not design your system, and it does not score it. It is a structured engineering conversation: a fixed order of questions that starts with the simplest possible answer and only moves toward model, tool, retrieval, memory, skill, or runtime complexity when an earlier answer makes the next step necessary.

The conversation is written down so it can be reviewed. The output is a filled-in document you can put in a design review, attach to a pull request, or disagree with.

**You probably don't need all of these.** Assessments exist to make that sentence actionable.

## Available assessments

| Assessment | Question it helps answer |
| --- | --- |
| [Agentic System Readiness](agentic-system-readiness/README.md) | What is the smallest AI/agentic architecture this problem actually needs — including none? |

Assessments belong to Track F — Learning Experience in [ROADMAP.md](../ROADMAP.md). They are not numbered labs and not capstones, and they never introduce a canonical concept: they only reason about concepts the labs have already taught.
